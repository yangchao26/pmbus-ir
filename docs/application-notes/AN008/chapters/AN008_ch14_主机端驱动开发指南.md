# 第 14 章 主机端驱动开发指南

> 本章面向需要在系统主机（BMC、嵌入式控制器、工控机等）上开发 PMBus 驱动的工程师。从开发环境搭建、首次联调 Checklist，到遥测轮询与故障响应状态机、NVM 安全策略和错误处理最佳实践，提供一套可落地的主机端驱动设计框架。本章不包含完整代码实现，相关 Python 编程示例详见第 16 章。

---

## 14.1 开发环境准备

### 14.1.1 Python + smbus2 库

Python 是 PMBus 开发调试和原型验证中最常用的语言。`smbus2` 库封装了 Linux I²C/SMBus 接口，支持 PMBus 所需的所有传输类型。

**环境要求**：

| 项目 | 要求 |
|------|------|
| Python 版本 | ≥ 3.8 |
| 操作系统 | Linux（内核自带 I²C 子系统）/ Windows（通过 USB 适配器） |
| smbus2 安装 | `pip install smbus2` |

`smbus2` 提供的关键接口与 PMBus 传输类型的对应关系：

| smbus2 方法 | PMBus 传输类型 | 典型用途 |
|-------------|---------------|----------|
| `write_byte()` | Write Byte | 写入 1 字节（如 OPERATION） |
| `read_byte()` | Read Byte | 读取 1 字节（如 STATUS_VOUT） |
| `write_word_data()` | Write Word | 写入 2 字节（如 VOUT_COMMAND） |
| `read_word_data()` | Read Word | 读取 2 字节（如 READ_VOUT） |
| `write_block_data()` | Write Block | 写入 N 字节（如 MFR_MODULE_DATE_LOC_SN） |
| `read_block_data()` | Read Block | 读取 N 字节（如 MFR_ID） |
| `write_quick()` | Send Byte | 无数据发送（如 CLEAR_FAULTS） |

> **提示**: `smbus2` 默认不启用 PEC。PMBus 设备若要求 PEC，需在调用时指定 `force=True` 参数或使用底层 `i2c_rdwr` 方法手动拼装带 PEC 的帧。PEC 的计算原理详见第 6 章。

### 14.1.2 硬件适配器

主机与 PMBus 设备之间的物理连接需要适配器。根据应用场景不同，有几种常见方案：

| 适配器类型 | 适用场景 | 说明 |
|-----------|----------|------|
| USB-to-I2C 适配器 | 工程调试、原型验证 | 如 FTDI FT232H、CH341A，通过 Linux I²C 子系统或厂商 SDK 驱动 |
| BMC 内置 I²C 控制器 | 服务器量产环境 | BMC 直接通过板载 I²C 总线访问电源模块 |
| 嵌入式 MCU I²C 外设 | 自定义控制器 | MCU 自带硬件 I²C 或 bit-bang 实现 |

**选型要点**：

1. **总线速率支持**：确认适配器支持目标速率（Omnion Power 模块支持 100 kHz 和 400 kHz）。建议首次联调从 100 kHz 开始。
2. **Clock Stretching 支持**：PMBus 设备会使用时钟拉伸（详见第 2 章），适配器或其驱动必须正确处理 SCL 被从设备拉低的情况。部分廉价适配器的软件 I²C 实现不支持时钟拉伸，应避免使用。
3. **Bus Timeout 实现**：SMBus 规范要求主机端实现 25~35 ms 的总线超时检测（详见第 2 章），这是从设备挂死时总线能自动恢复的前提。
4. **电气特性**：确认适配器的 I/O 电平与模块逻辑引脚兼容（Omnion Power 模块逻辑引脚最大 3.6 V）。

### 14.1.3 调试工具

| 工具 | 用途 | 关键能力 |
|------|------|----------|
| 示波器（4 通道以上） | 物理层信号质量检查 | I²C/SMBus 协议解码、时序测量、信号完整性 |
| 逻辑分析仪 | 长时间通信抓包 | I²C/SMBus 协议解码、数据导出、错误定位 |
| `i2cdetect` | Linux 下设备地址扫描 | 快速确认设备是否在总线上响应 |
| `i2cget` / `i2cset` | Linux 下命令行读写 | 无需写代码即可验证基本通信 |
| `smbus-sniffer` | 总线监听 | 非侵入式捕获总线上所有事务 |

> **提示**: 示波器的 I²C 协议解码功能可以在调试初期快速定位物理层问题（信号边沿、上拉是否充足、是否存在总线冲突）。建议至少在首次联调时使用示波器验证总线信号质量。

## 14.2 初始化流程（Bring-up Checklist）

首次将 Omnion Power 电源模块接入 PMBus 总线后，建议按照以下 Checklist 逐步验证，不要跳步。

### 14.2.1 物理层检查

| 序号 | 检查项 | 验证方法 | 通过标准 |
|------|--------|----------|----------|
| 1 | SDA/SCL 空闲时为高电平 | 示波器测量 | 无通信时 SDA、SCL 均为高电平 |
| 2 | 上拉电阻值与总线电容匹配 | 读取电阻标称值 + 估算线缆电容 | 满足目标速率的上升时间要求（详见第 3 章） |
| 3 | 设备地址配置正确 | 检查 ADDR1 引脚外接电阻值 | 电阻值对应的地址与预期一致（参见具体产品 Datasheet） |
| 4 | 无总线 stuck | 示波器观察 SDA/SCL | 空闲时两根线均为高，无持续低电平 |
| 5 | 主机端 timeout 已启用 | 检查驱动配置 | SMBus timeout 设置为 25~35 ms |

### 14.2.2 基本通信验证

通过以下步骤确认主机与模块之间的 PMBus 通信正常。

**步骤 1：低速扫描地址**

首次上电后，建议从低速（100 kHz）开始，使用地址扫描确认设备响应：

- 使用 `i2cdetect -y <bus>` 扫描 0x08~0x77 范围
- 确认扫描到的地址与模块地址配置一致
- 避免一开始就高频轮询，给模块足够的初始化时间

**步骤 2：读取设备标识命令**

地址确认后，依次读取以下命令，验证设备通信链路完整性：

| 命令 | 命令码 | 传输类型 | 预期结果 |
|------|--------|----------|----------|
| PMBUS_REVISION | 0x98 | Read Byte | 0x22（PMBus 1.2） |
| CAPABILITY | 0x19 | Read Byte | 0xB0 |
| MFR_ID | 0x99 | Read Block | "OMPW" |
| MFR_MODEL | 0x9A | Read Block | 产品型号字符串 |
| MFR_SERIAL | 0x9E | Read Block | 产品序列号 |

> **提示**: MFR_ID 返回 "OMPW" 是 Omnion Power 模块的标识特征。若返回值不符合预期，应检查设备地址是否正确。

**步骤 3：读取状态寄存器**

```
读取 STATUS_WORD (0x79) → 检查是否为 0x0000（无故障）
读取 STATUS_CML (0x7E)  → 检查通信层是否有错误
```

STATUS 寄存器的详细位域定义参见第 8 章和附录 D。

**步骤 4：验证 PEC（如启用）**

如果系统要求启用 PEC（推荐启用），使用已知的 Read Word 命令验证：

1. 发送不带 PEC 的 Read Word 命令（如 READ_VOUT），确认设备响应
2. 发送带 PEC 的 Read Word 命令，确认设备接受（不会因 PEC 错误而 NACK）
3. 验证设备返回的 PEC 与本地计算结果一致

PEC 计算原理和实现方法详见第 6 章。

### 14.2.3 遥测数据合理性检查

通信链路验证通过后，读取遥测数据并与实际测量值比对，确认数据链路端到端正确：

| 检查项 | PMBus 命令 | 参考基准 | 合理范围 |
|--------|-----------|----------|----------|
| 输入电压 | READ_VIN (0x88) | 外部 DMM 测量 VIN 引脚 | 误差 ±4% |
| 输出电压 | READ_VOUT (0x8B) | 外部 DMM 测量 VOUT 引脚 | 误差 ±2% |
| 输出电流 | READ_IOUT (0x8C) | 负载已知时验证趋势 | 空载时接近 0，负载时正比增长 |
| 模块温度 | READ_TEMPERATURE_1 (0x8D) | 环境温度参考 | 室温附近起步，负载后缓慢上升 |

遥测命令的数据格式和编码/解码方法详见第 5 章和第 12 章。

> **提示**: READ_IOUT 在 20A 以下输出电流时读数被消隐（显示为 0），这是正常行为，不是故障。

### 14.2.4 控制与恢复验证

| 验证项 | 操作 | 预期行为 |
|--------|------|----------|
| 软件关断 | 写 OPERATION (0x01) Bit 7 = 0 | 输出关闭，STATUS_WORD Bit 6 (OFF) 置位 |
| 软件开启 | 写 OPERATION (0x01) Bit 7 = 1 | 输出恢复（前提是 ON/OFF 引脚使能） |
| 裕量高 | 写 OPERATION (0x01) Bit 5 = 1 | 输出电压跳至 VOUT_MARGIN_HIGH |
| 裕量低 | 写 OPERATION (0x01) Bit 4 = 1 | 输出电压跳至 VOUT_MARGIN_LOW |
| 清除故障 | 发送 CLEAR_FAULTS (0x03) | STATUS 寄存器中 latch 位清除，SMBALERT# 释放 |
| 写保护 | 读取 MFR_DEVICE_TYPE (0xD0) Bit 1 | 确认写保护状态，默认 WPE=1（启用） |

ON/OFF 控制的详细逻辑参见第 9 章。ON/OFF 引脚与 OPERATION 命令的交互参见第 13 章。

### 14.2.5 NVM 操作验证

> **警告**: 非必要不在 bring-up 早期执行 NVM Store 操作。EEPROM 写入次数有限，调试阶段的频繁写入会消耗写寿命。

| 验证项 | 操作 | 注意事项 |
|--------|------|----------|
| 当前配置读取 | 读取关键配置命令（VOUT_COMMAND、保护阈值等） | 确认与 Datasheet 默认值一致 |
| Store 操作 | 关闭输出 → 修改参数 → STORE_DEFAULT_ALL | 执行后等待 ≥500ms 再通信 |
| Restore 操作 | RESTORE_DEFAULT_ALL | 验证参数恢复到 Store 时的快照 |
| 写保护验证 | 在 WPE=1 时尝试写入受保护命令 | 命令应被静默忽略 |

NVM 的三层参数模型和操作注意事项详见第 10 章。

## 14.3 遥测轮询状态机

### 14.3.1 设计目标

主机端驱动需要周期性地从电源模块读取遥测数据。一个设计良好的轮询状态机应满足以下要求：

- **避免总线拥塞**：不同遥测参数的更新频率不同，不需要同一速率轮询所有命令
- **优先级分层**：状态和故障检查优先级高于普通遥测
- **支持多设备**：同一总线上多个模块的轮询需要合理调度
- **带宽可控**：轮询占用总线的带宽不应影响其他总线设备

### 14.3.2 遥测更新频率与轮询间隔

PMBus 规范本身不限制主机的轮询速率，但设备的遥测数据有内部更新周期。主机以远高于数据更新频率的速率轮询只会得到重复数据，浪费总线带宽。

| 遥测参数 | 典型内部更新周期 | 推荐最小轮询间隔 |
|----------|-----------------|-----------------|
| READ_VOUT | 5~10 ms | ≥ 10 ms |
| READ_IOUT | 5~20 ms | ≥ 20 ms |
| READ_VIN | 5~10 ms | ≥ 10 ms |
| READ_TEMPERATURE_1 | 100~500 ms | ≥ 100 ms |
| STATUS_WORD | 实时 | ≥ 50 ms |

> **提示**: 以上更新周期为典型值，具体数值参见产品 Datasheet。过快的轮询不会损坏设备，但会增加总线负载并可能导致 Clock Stretching 时间增加，降低整体系统效率。

### 14.3.3 状态定义

遥测轮询状态机包含以下状态：

```
INIT         — 初始化，执行设备发现和基本通信验证
DISCOVER     — 读取设备能力信息（REVISION、CAPABILITY、MFR 信息、PAGE 支持）
NORMAL_POLL  — 正常轮询模式，按优先级周期性读取遥测和状态
ALERT_WAIT   — 等待 SMBALERT# 触发或下次轮询周期
NVM_BUSY     — NVM 操作期间的等待状态
DEGRADED     — 通信异常时的降级模式
OFFLINE      — 设备丢失，尝试重新发现
```

> - OFFLINE → DISCOVER（定时重新扫描设备地址）
> - SMBALERT# 触发 → 进入故障处理（参见第 14.4 节）

### 14.3.5 正常轮询逻辑

NORMAL_POLL 状态下的轮询应遵守以下优先级结构，不要把 NVM 操作、故障恢复和高频遥测全部放在同一条无优先级链路里：

**第一优先级：状态摘要**

```
for each device:
    read STATUS_WORD (0x79)
    if STATUS_WORD != 0:
        进入故障处理分支
```

**第二优先级：关键遥测**

```
for each device:
    for each page (如支持):
        read READ_VOUT (0x8B)
        read READ_IOUT (0x8C)
```

**第三优先级：辅助遥测（更低频率）**

```
read READ_VIN (0x88)
read READ_TEMPERATURE_1 (0x8D)
```

> **提示**: STATUS_WORD 是最有效的健康检查入口。建议在系统空闲时定期读取，仅在 STATUS_WORD 非零时才逐个查询详细状态寄存器（STATUS_VOUT、STATUS_IOUT 等），以减少总线流量。状态寄存器的详细位域参见第 8 章和附录 D。

### 14.3.6 轮询带宽预算

在多设备系统中，需要估算轮询占用的总线带宽，确保不超出总线容量。

以 400 kHz 总线、单次 Read Word 事务（约 110 µs 含寻址和数据阶段）为例：

| 场景 | 设备数 | 每设备每轮命令数 | 轮询周期 | 每轮总事务时间 | 总线占用率 |
|------|--------|-----------------|----------|---------------|-----------|
| 精简轮询 | 4 | 3（STATUS_WORD + VOUT + IOUT） | 50 ms | ~1.3 ms | ~2.6% |
| 完整轮询 | 4 | 6（全部遥测 + 状态） | 100 ms | ~2.6 ms | ~2.6% |
| 高密度 | 12 | 6 | 50 ms | ~7.9 ms | ~15.8% |

> **提示**: 总线占用率超过 30% 时应考虑优化轮询策略，例如降低温度等慢变参数的轮询频率、或使用 SMBALERT 中断驱动替代部分轮询。

## 14.4 故障响应状态机

### 14.4.1 故障响应流程

当主机检测到故障条件（STATUS_WORD 非零或 SMBALERT# 触发）时，驱动需要按照结构化流程处理。故障寄存器和保护机制的详细说明参见第 8 章。

### 14.4.2 状态定义

```
IDLE             — 无故障，正常监控
FAULT_DETECTED   — 检测到故障（STATUS_WORD 非零或 SMBALERT#）
FAULT_DIAGNOSE   — 读取详细状态寄存器，定位故障源
FAULT_LOG        — 记录故障信息和遥测快照
FAULT_ACTION     — 执行故障响应动作（关断、通知、重试等）
FAULT_RECOVERY   — 等待故障恢复或执行恢复操作
```

### 14.4.3 状态转换图

[TODO: 图表 — 故障响应状态机状态转换图]
> 图中应包含以下状态及转换路径：
> - IDLE → FAULT_DETECTED（STATUS_WORD 非零 或 SMBALERT# 触发）
> - FAULT_DETECTED → FAULT_DIAGNOSE（开始详细诊断）
> - FAULT_DIAGNOSE → FAULT_LOG（读取完所有相关状态寄存器和遥测快照后）
> - FAULT_LOG → FAULT_ACTION（根据故障类型决定响应动作）
> - FAULT_ACTION → FAULT_RECOVERY（如果故障可恢复，如 auto-retry 模式）
> - FAULT_RECOVERY → IDLE（故障恢复成功，发送 CLEAR_FAULTS）
> - FAULT_RECOVERY → FAULT_DETECTED（故障仍在持续，如 auto-retry 但故障未消除）
> - FAULT_ACTION → IDLE（对于 warning 级别，仅需记录日志）
> - FAULT_ACTION → 系统关断（对于不可恢复的严重故障）

### 14.4.4 故障诊断流程

FAULT_DIAGNOSE 状态下，应按照以下顺序查询状态寄存器以定位故障源：

```
1. 读取 STATUS_WORD (0x79) — 获取故障摘要
2. 根据 STATUS_WORD 高字节定位故障类别：
   - Bit 15 置位 → 读取 STATUS_VOUT (0x7A)
   - Bit 14 置位 → 读取 STATUS_IOUT (0x7B)
   - Bit 13 置位 → 读取 STATUS_INPUT (0x7C)
   - Bit 2 置位  → 读取 STATUS_TEMPERATURE (0x7D)
   - Bit 1 置位  → 读取 STATUS_CML (0x7E)
3. 读取关键遥测快照：
   - READ_VOUT (0x8B)
   - READ_IOUT (0x8C)
   - READ_VIN (0x88)
   - READ_TEMPERATURE_1 (0x8D)
```

### 14.4.5 故障分类与响应策略

| 故障级别 | 典型条件 | 响应策略 |
|----------|----------|----------|
| Warning | IOUT_OC_WARN_LIMIT 超限、OT_WARN_LIMIT 超限 | 记录日志，通知上层，不改变设备状态 |
| Fault（可恢复） | OVP、OCP、OTP 触发（auto-retry 模式） | 记录日志，等待设备自动重启恢复，必要时通知上层 |
| Fault（需干预） | 设备 latch off、连续 auto-retry 失败 | 通知上层决策（人工介入或系统关断） |
| 通信故障 | 连续 NACK、PEC error 超过阈值 | 降低轮询频率，进入 DEGRADED 模式 |

> **提示**: CLEAR_FAULTS 命令只清除 latch 的状态位和 SMBALERT# 信号，不会改变设备的实际输出状态。如果故障条件仍然存在（如过温），清除后状态位会立即重新置位。不要通过反复清除故障来掩盖真实问题。

### 14.4.6 SMBALERT 中断处理

当模块检测到报警条件时，会拉低 SMBALERT# 引脚通知主机。主机的处理流程：

1. **检测 SMBALERT#**：通过 GPIO 中断或轮询检测 SMBALERT# 下降沿
2. **识别报警设备**：通过 Alert Response Address（ARA = 0x0C）协议查询（详见第 7 章）
3. **读取故障状态**：按 14.4.4 节流程诊断
4. **决定响应**：根据故障级别执行相应动作
5. **清除报警**：故障处理完成后发送 CLEAR_FAULTS

SMBALERT 中断机制的详细说明参见第 7 章。

## 14.5 NVM 操作的安全策略

NVM（非易失性存储）操作涉及 EEPROM 的写入，需要特别谨慎。NVM 的三层参数模型和操作命令详见第 10 章。

### 14.5.1 NVM 三层参数模型回顾

Omnion Power 模块内部维护以下参数存储层次：

| 层次 | 内容 | 特点 |
|------|------|------|
| Factory Default | 出厂预设参数 | 通常不可修改，作为恢复基准 |
| Default Store (EEPROM) | 用户保存的配置 | 通过 STORE_DEFAULT_ALL 写入，上电时自动加载 |
| Runtime RAM | 当前运行参数 | 主机通过 PMBus 命令实时修改，掉电后丢失 |

上电时模块自动从 Default Store 加载配置到 Runtime RAM。主机修改的运行参数不会自动持久化，必须显式执行 STORE_DEFAULT_ALL 才能保存。

### 14.5.2 写入时机建议

| 原则 | 说明 |
|------|------|
| 仅在配置稳定时写入 | 不要在调试阶段频繁调用 Store。先验证所有参数正确，再一次性保存 |
| 输出关闭时写入 | 建议在模块输出关闭状态下执行 Store，避免运行中配置不一致 |
| 写入后等待 | Store 执行需要时间（≤ 500ms），期间不应发送额外 PMBus 命令 |
| 控制写入频率 | EEPROM 写入次数有限，不应将 Store 放入周期性任务中 |

### 14.5.3 写入流程

NVM 写入的安全操作流程：

```
1. 关闭模块输出（OPERATION Bit 7 = 0）
2. 等待输出完全关闭
3. 如有写保护，先解除（MFR_DEVICE_TYPE WPE = 0）
4. 修改所需参数
5. 读回验证参数值正确
6. 执行 STORE_DEFAULT_ALL (0x11)
7. 等待 ≥ 500ms（Tstore）
8. 读回关键参数，验证持久化成功
9. 恢复写保护（MFR_DEVICE_TYPE WPE = 1）—— 如需要
10. 重新开启输出
```

### 14.5.4 写入失败处理

| 失败场景 | 检测方法 | 处理策略 |
|----------|----------|----------|
| Store 后读回值不一致 | Store 后重新读取关键参数 | 重新写入一次，若仍失败则标记设备 NVM 异常 |
| Store 期间掉电 | 上电后参数恢复到上次成功保存的状态 | 需要重新配置并再次执行 Store |
| Store 期间设备 NACK | 事务返回通信错误 | 等待后重试，检查 STATUS_CML |
| NVM 寿命耗尽 | Store 频繁失败 | 记录错误，通知维护 |

> **警告**: NVM 写入过程中断电可能导致 Default Store 数据损坏。虽然模块内部通常有 valid flag 或 checksum 保护（上电时检测到无效数据会回退到 Factory Default），但仍应避免在写入过程中断电。

### 14.5.5 参数白名单意识

并非所有 PMBus 可写命令都应该或能够持久化到 NVM。主机开发者应参考具体产品 Datasheet 中"非易失性存储摘要"列出的可存储命令列表。试图 Store 不在白名单中的参数不会产生错误，但这些参数在下次上电后不会保留。

## 14.6 错误处理最佳实践

### 14.6.1 错误分类

主机端驱动可能遇到的错误分为以下几类：

| 错误类型 | 典型表现 | 根因 |
|----------|----------|------|
| NACK | 设备无响应 | 地址错误、设备未就绪、总线冲突 |
| PEC error | 设备返回 NACK 或本地校验失败 | 帧损坏、CRC 实现错误、总线噪声 |
| Timeout | 事务超时未完成 | 设备 Clock Stretching 过长、总线 stuck、设备挂死 |
| Unsupported command | 设备 ACK 但 STATUS_CML 置 INVALID_CMD | 命令不在设备支持列表中 |
| Invalid data | 设备 ACK 但 STATUS_CML 置 INVALID_DATA | 写入值超出有效范围 |

### 14.6.2 重试策略

不同错误类型需要不同的重试策略：

| 错误类型 | 重试建议 | 说明 |
|----------|----------|------|
| NACK | 短延迟后有限重试（最多 3 次） | 首次 NACK 可能是暂时的总线冲突 |
| PEC error | 重试并计数，不立即判定设备故障 | 偶发 PEC error 可能是总线噪声 |
| Timeout | 执行总线恢复后再重试 | 详见下方总线恢复流程 |
| Unsupported command | **不重试**，更新 capability cache | 无限重试会浪费总线带宽 |
| Invalid data | 检查写入值范围，修正后重试 | 不应盲目重试无效数据 |
| NVM busy | 进入 NVM_BUSY 等待状态 | 等待 Tstore 后恢复，不在普通轮询中重试 |

### 14.6.3 错误计数与降级策略

连续错误达到阈值时，驱动应主动降级，避免在故障状态下持续消耗总线带宽：

| 错误模式 | 计数维度 | 降级阈值 | 降级动作 |
|----------|----------|----------|----------|
| 偶发 PEC error | device + command | 单次 | 重试，保留上一次有效遥测值 |
| 连续 NACK | device | 连续 3 次 | 降低轮询频率（如 10 倍），标记 DEGRADED |
| 连续 timeout | bus + device | 连续 2 次 | 执行总线恢复，必要时重新 DISCOVER |
| Unsupported command | device + command | 首次 | 从轮询配置中禁用该命令，不再周期访问 |
| NVM busy | device | 单次 | 暂停普通轮询，进入 NVM_BUSY 等待 |
| Fault latch | device + page | 单次 | 进入故障处理流程 |

### 14.6.4 总线恢复流程

当检测到总线 timeout 或 bus stuck（SDA 持续低电平）时，主机需要执行总线恢复：

```
1. 检测到 timeout（事务超过 35 ms 未完成）
2. 发送 STOP 条件（尝试释放总线）
3. 发送 9 个 SCL 时钟脉冲（强制从设备释放 SDA）
4. 发送 STOP 条件
5. 等待一段恢复间隔（≥ 100 ms）
6. 尝试发送一次简单读命令（如 STATUS_BYTE）验证总线恢复
7. 若仍失败，标记总线为 OFFLINE，等待更长时间后重试
```

总线恢复的原理详见第 2 章。

### 14.6.5 日志记录建议

一个可靠的 PMBus 驱动应记录以下信息，便于事后分析：

| 日志类型 | 记录内容 | 用途 |
|----------|----------|------|
| 通信错误 | 时间戳、设备地址、命令码、错误类型、重试次数 | 分析总线质量 |
| 故障事件 | 时间戳、设备地址、STATUS_WORD、详细状态寄存器、遥测快照 | 根因分析 |
| NVM 操作 | 时间戳、Store/Restore 命令、参数变更内容 | 审计追踪 |
| 状态转换 | 时间戳、旧状态、新状态、触发条件 | 驱动行为调试 |

日志格式建议包含足够上下文，使离线分析时无需对照其他数据源即可定位问题。

### 14.6.6 优雅降级

当通信持续异常时，驱动不应无限重试或崩溃，而应优雅降级：

1. **保留最后有效数据**：通信中断期间，向上层报告最后一次成功读取的遥测值，并标注数据时间戳
2. **降低轮询频率**：从正常轮询频率逐步降低到最小频率（如每 10 秒一次探测）
3. **通知上层**：通过日志或回调通知系统管理层设备通信异常
4. **自动恢复**：在降级模式下持续尝试探测，一旦通信恢复自动回到正常轮询模式
5. **安全默认**：如果设备长时间无法恢复通信，系统应根据安全策略决定是否执行保护动作（如关断输出）
