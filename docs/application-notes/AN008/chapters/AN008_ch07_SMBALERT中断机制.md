# 第 7 章 SMBALERT 中断机制

> 本章讲解 SMBus/PMBus 的异步事件通知机制——SMBALERT。首先对比事件驱动与轮询驱动两种监控范式的优劣，然后详细讲解 Alert 响应地址（Alert Response Address, ARA）协议的完整流程、多设备同时报警时的仲裁机制，以及 SMBALERT_MASK 命令的使用方法。最后给出主机端中断处理的推荐流程。

---

## 7.1 为什么需要 SMBALERT

### 7.1.1 事件驱动与轮询驱动

电源系统状态监控有两种基本范式：轮询驱动（Polling）和事件驱动（Event-driven / Interrupt-driven）。

**轮询驱动**：主机以固定间隔周期性读取设备状态寄存器，发现异常后再执行处理逻辑。

**事件驱动**：设备在检测到异常条件时，主动通过硬件信号通知主机，主机随即响应并读取详细信息。

两种范式各有适用场景，在 PMBus 系统中通常**组合使用**：正常运行时以轮询采集遥测数据，故障发生时通过 SMBALERT 实现快速响应。

### 7.1.2 两种范式的优劣对比

| 维度 | 轮询驱动 | 事件驱动（SMBALERT） |
|------|---------|---------------------|
| 故障响应延迟 | 最坏情况下等于轮询周期 | 近乎实时（微秒级信号传输） |
| 总线带宽占用 | 持续占用，轮询越频繁开销越大 | 仅在事件发生时占用 |
| CPU 开销 | 周期性唤醒，空闲时仍有开销 | 空闲时几乎为零 |
| 实现复杂度 | 简单，纯软件循环即可 | 需要硬件中断支持 + 协议处理 |
| 状态覆盖完整性 | 取决于轮询频率和时序 | 设备主动上报，不遗漏 |
| 适合场景 | 遥测数据采集、健康巡检 | 严重故障、保护动作、需立即介入的状态变化 |

### 7.1.3 轮询驱动的固有局限

纯轮询方案面临一个根本矛盾：**轮询频率越高，响应越快，但总线带宽消耗越大**。

假设系统中有 N 个电源模块，每个模块需读取 STATUS_BYTE（1 字节读事务 ≈ 10 bit × 9 + ACK = 约 100 µs @ 100 kHz），则完整一轮巡检耗时至少 N × 100 µs。如果 N = 16，单轮巡检约 1.6 ms——这意味着最坏情况下故障发现延迟可达 1.6 ms。

对于输出过压、过温关断等需要毫秒级响应的故障，纯轮询方案的延迟可能超出系统安全裕量。

### 7.1.4 SMBALERT 的定位

SMBALERT 不是替代轮询，而是**补充**轮询。推荐的使用模式：

- **正常运行**：按合理频率轮询遥测数据（详见第 12 章），采集电压、电流、温度等实时参数。
- **异常发生**：SMBALERT 触发主机立即进入告警处理流程，读取状态寄存器（详见第 8 章）和关键遥测数据快照。
- **告警恢复后**：主机返回正常轮询模式。

> **提示**：SMBALERT 信号本身只通知"有设备需要关注"，不包含具体是哪个设备、发生了什么故障。主机需要通过 ARA 协议（见 7.3 节）来定位报警来源，再读取 STATUS 寄存器（详见第 8 章 + 附录 D）获取故障详情。

## 7.2 SMBALERT# 信号

### 7.2.1 开漏输出、低电平有效

SMBALERT# 是一根独立的单向信号线，从设备到主机，低电平有效（后缀 `#` 表示低电平有效）。

设备内部通过**开漏（Open-Drain）**输出驱动 SMBALERT# 线。当设备检测到需要通知主机的条件时，内部晶体管导通，将 SMBALERT# 拉低至接近地电平；未报警时，输出呈高阻态（Hi-Z）。

开漏输出的物理特性详见第 2 章。

### 7.2.2 上拉电阻要求

SMBALERT# 线需要在主机端连接上拉电阻（Rp），确保无设备报警时信号线处于高电平。

上拉电阻的选择需满足以下约束：

| 参数 | 说明 |
|------|------|
| 上拉电压 | 与总线逻辑电平一致（通常为 3.3 V） |
| Rp 范围 | [参见具体产品 Datasheet] |
| 典型值 | 4.7 kΩ ~ 10 kΩ |
| 上升时间 | 受 Rp 和总线电容决定 |

> **提示**：上拉电阻的选型原则与 SCL/SDA 线相同，详见第 2 章（PMBus 协议基础）的上拉电阻部分。

### 7.2.3 线或（Wired-OR）多设备连接

多个设备的 SMBALERT# 输出可以连接到同一根信号线上，形成**线或（Wired-OR）**拓扑。

```
        Vpullup
          |
         Rp
          |
SMBALERT# --------+--------+--------+
                  |        |        |
              Device A  Device B  Device C
```

线或的关键特性：

- 只要**任意一个**设备拉低 SMBALERT#，整条线就处于低电平。
- 所有设备都释放（Hi-Z）时，上拉电阻将信号线恢复为高电平。
- 主机只需监测一根信号线的电平变化，即可判断总线上是否有设备报警。

这种拓扑使 SMBALERT# 天然支持多设备共享，与 SMBus 的开漏总线架构一致（详见第 2 章）。

## 7.3 Alert 响应地址（ARA = 0x0C）

### 7.3.1 ARA 概述

当 SMBALERT# 被拉低时，主机需要确定是哪个（或哪些）设备发出了报警。SMBus 规范定义了 **Alert 响应地址（Alert Response Address, ARA）** 协议来完成这一任务。

ARA 使用保留地址 **0x0C**，这是一个特殊地址，不分配给任何设备作为正常通信地址。在 ARA 协议过程中，报警设备会临时将其地址识别逻辑切换为响应 0x0C。

### 7.3.2 ARA 协议完整流程

ARA 协议是一个多步骤过程，具体流程如下：

**步骤 1：设备发出报警**

设备内部检测到故障条件（如过压、过流、过温等），将 SMBALERT# 拉低。此时设备处于"等待主机响应"状态。

**步骤 2：主机检测到 SMBALERT# 低电平**

主机端通过 GPIO 中断或轮询检测到 SMBALERT# 变为低电平，确认总线上有设备正在报警。

**步骤 3：主机发起 ARA 读请求**

主机向总线发送 ARA 地址（0x0C）的读请求：

```
START → 0x0C (ARA) + R → 等待报警设备响应
```

**步骤 4：报警设备响应并返回自身地址**

所有正在报警的设备都会监听 ARA 地址。设备在发送 ACK 之前，会比较自身设备地址：

- 如果自己检测到总线上正在发送的地址位与自己的设备地址一致（即自己在地址仲裁中胜出），则发送 ACK，随后在数据字节返回自己的设备地址（7-bit 地址左移 1 位，即 8-bit 写地址格式）。
- 如果在地址比较中发现有更低地址的设备在同时发送，则退让，不发送 ACK。

**步骤 5：主机记录报警设备地址**

主机收到 ACK 后，继续读取一个数据字节，该字节即为报警设备的设备地址。

**步骤 6：主机处理该设备的故障**

主机使用收到的设备地址，读取 `STATUS_WORD (0x79)` 或 `STATUS_BYTE (0x78)` 等状态寄存器（详见第 8 章），获取具体故障信息。读取操作遵循标准 PMBus 读事务（详见第 4 章）。

**步骤 7：设备释放 SMBALERT#（如果条件已满足）**

当主机成功读取了该设备的相关状态寄存器后，如果设备的报警条件已全部被主机读取（具体行为取决于设备实现），设备释放 SMBALERT#。如果该设备仍有未报告的报警条件，或总线上还有其他设备在报警，SMBALERT# 保持低电平。

**步骤 8：主机检查 SMBALERT# 是否释放**

主机完成一个设备的处理后，再次检查 SMBALERT#：

- 如果 SMBALERT# 已释放（高电平），说明所有报警设备都已处理完毕，流程结束。
- 如果 SMBALERT# 仍为低电平，说明还有其他设备等待处理，主机返回步骤 3，再次发起 ARA 读请求。

## 7.4 多设备同时报警的仲裁

### 7.4.1 仲裁原理

当多个设备同时拉低 SMBALERT# 时，主机的 ARA 读请求需要一种机制来确定**先响应哪个设备**。SMBus 利用 I²C 总线固有的**地址仲裁机制**来解决这个问题。

仲裁发生在 ARA 地址发送阶段：

1. 主机发送 ARA 地址字节（0x0C）时，所有报警设备都监听总线。
2. 主机发送读位（R = 1）后，进入应答阶段。
3. 此时所有报警设备**同时开始发送 ACK**，随后准备发送自己的设备地址作为数据字节。
4. 在数据字节发送阶段，多个设备同时驱动 SDA 线。由于开漏线或特性，任何设备发送 `0`（SDA 低）都会覆盖其他设备发送的 `1`（SDA 高）。
5. **设备地址最低的设备赢得仲裁**：因为它在最高有效位上最先发送 `0`（低地址的 MSB 更小），从而覆盖了其他设备发送的 `1`。
6. 赢得仲裁的设备继续发送完整的地址字节。
7. 未赢得仲裁的设备检测到 SDA 线上的电平与自己发送的不一致，立即停止发送并切换为监听模式。

### 7.4.2 地址最低优先规则

仲裁结果遵循**地址最低优先（lowest address wins）**规则：

| 设备地址 | 仲裁结果 | 说明 |
|----------|---------|------|
| 0x10 | 赢得仲裁 | 在 MSB 上最先发送 `0` |
| 0x20 | 未赢得 | 在与 0x10 比较时，第 4 位 `1` 被 0x10 的 `0` 覆盖 |
| 0x30 | 未赢得 | 同理 |
| 0x58 | 未赢得 | 同理 |

> **提示**：这意味着在多设备系统中，地址较低的设备会被优先处理。如果某个低地址设备频繁报警，可能会"饿死"高地址设备的告警处理。系统设计时应考虑这一特性。

### 7.4.3 失败设备继续拉低 SMBALERT#

未赢得仲裁的设备虽然在这轮 ARA 事务中未能响应，但**不会释放 SMBALERT#**。它们继续保持 SMBALERT# 低电平，等待主机在处理完当前设备后再次发起 ARA 读请求。

具体行为：

- **赢得仲裁的设备**：返回地址后，如果主机已读取其所有报警条件，则释放 SMBALERT#。
- **未赢得仲裁的设备**：保持 SMBALERT# 低电平，继续等待。

### 7.4.4 主机循环读取流程

主机必须循环执行 ARA 协议，直到 SMBALERT# 被完全释放。完整流程如下：

```
检测到 SMBALERT# = LOW
    │
    ▼
发起 ARA 读请求 (地址 0x0C + R)
    │
    ▼
收到报警设备地址 (最低地址优先)
    │
    ▼
读取该设备 STATUS_WORD / STATUS_BYTE
    │
    ▼
根据故障类型执行处理逻辑
    │
    ▼
检查 SMBALERT# 电平
    │
    ├── HIGH ──► 所有报警已处理，返回正常模式
    │
    └── LOW ──► 还有设备等待处理
         │
         ▼
      返回 "发起 ARA 读请求"
```

> **提示**：为防止某个故障设备反复报警导致主机陷入死循环，建议设置最大循环次数或超时机制。主机端驱动开发中的状态机设计详见第 14 章。

## 7.5 SMBALERT_MASK 命令

### 7.5.1 命令概述

`SMBALERT_MASK` 是 PMBus 提供的可选命令，用于屏蔽特定的告警条件，使其**不触发 SMBALERT# 信号**，即使对应的故障条件仍然存在。

| 属性 | 值 |
|------|-----|
| 命令码 | 0x1B |
| 访问类型 | 读/写 |
| 数据格式 | 1 字节 |
| 支持情况 | 可选（通过 CAPABILITY 命令 Bit 4 确认） |

### 7.5.2 屏蔽位含义

`SMBALERT_MASK` 的每一位对应 `STATUS_BYTE` 中的相应位。当某位置 `1` 时，该类故障**不会触发 SMBALERT#**。

| 位 | 对应 STATUS_BYTE 位 | 屏蔽条件 | 说明 |
|----|---------------------|---------|------|
| Bit 7 | Bit 7 (BUSY) | 忙状态 | 屏蔽繁忙通知 |
| Bit 6 | Bit 6 (OFF) | 关断状态 | 屏蔽关断通知 |
| Bit 5 | Bit 5 (FAULT) | 严重故障 | ⚠️ 一般不建议屏蔽 |
| Bit 4 | Bit 4 (WARNING) | 告警 | 屏蔽警告通知 |
| Bit 3 | Bit 3 (COMMAND) | 命令错误 | 屏蔽无效命令通知 |
| Bit 2 | Bit 2 (COMM) | 通信错误 | 屏蔽通信异常通知 |
| Bit 1 | Bit 1 (MEMORY) | 存储器错误 | 屏蔽存储器异常通知 |
| Bit 0 | Bit 0 (PROCESSOR) | 处理器错误 | 屏蔽内部逻辑异常通知 |

> **提示**：屏蔽告警不会影响故障保护动作本身。设备内部的过压保护、过流保护等机制仍然正常工作，只是不通过 SMBALERT# 通知主机。主机仍可通过轮询 STATUS 寄存器发现这些故障（详见第 8 章）。

### 7.5.3 使用建议

- **不建议屏蔽严重故障（Bit 5）**：过压、过流、过温等严重故障通常需要主机立即介入，屏蔽 SMBALERT 会导致故障响应延迟。
- **可以屏蔽频繁但不关键的警告（Bit 4）**：例如在已知边界条件下的电压轻微波动。
- **屏蔽前评估后果**：确认被屏蔽的故障条件不会导致系统安全问题。

## 7.6 主机端中断处理流程

### 7.6.1 中断服务例程设计

主机端处理 SMBALERT 的推荐流程分为两个层次：**中断服务例程（ISR）** 和**后台告警处理任务**。

**ISR 层**（硬实时，尽可能短）：

1. 检测到 SMBALERT# 下降沿中断。
2. 设置标志位或发送信号量通知后台任务。
3. 退出 ISR。

> **提示**：ISR 中**不应**直接执行总线事务。ARA 协议和 STATUS 读取涉及多个总线事务，耗时可能达数毫秒，不适合在中断上下文中执行。

**后台告警处理任务**（非实时，可被调度）：

收到 ISR 通知后执行完整的告警处理流程。

### 7.6.3 读取 STATUS_WORD 获取详细故障信息

`STATUS_WORD (0x79)` 是最优先读取的状态寄存器，它组合了 `STATUS_BYTE` 和 `STATUS_VOUT` 的信息（2 字节），一次读取即可获得快速概览。

读取操作遵循标准 PMBus Read Word 事务（详见第 4 章）：

1. 主机发送设备地址 + W。
2. 主机发送命令码 0x79。
3. 主机发送 REPEATED START（Sr）。
4. 主机发送设备地址 + R。
5. 设备返回低字节（STATUS_BYTE）和高字节（STATUS_VOUT）。
6. 主机发送 NACK + STOP。

STATUS_WORD 的位域解析详见第 8 章 + 附录 D。

### 7.6.4 故障处理决策树

读取状态寄存器后，主机需要根据故障类型和严重程度决定后续动作：

```
STATUS_WORD 解析结果
    │
    ├── 无故障位 ──► 误报或已恢复，记录日志
    │
    ├── WARNING 置位（Bit 4）
    │   │
    │   ▼
    │   读取对应 STATUS_xxx 定位具体警告
    │   记录警告日志，继续正常轮询
    │
    ├── FAULT 置位（Bit 5）
    │   │
    │   ▼
    │   读取对应 STATUS_xxx 定位具体故障
    │   ├── 过压 / 过流 / 过温
    │   │   │
    │   │   ▼
    │   │   检查 FAULT_RESPONSE 配置
    │   │   (详见第 8 章 + 附录 E)
    │   │   │
    │   │   ├── 设备已自动关断 ──► 记录故障快照
    │   │   │                        评估是否允许重启
    │   │   │
    │   │   └── 设备仍在运行 ──► 评估负载安全
    │   │                           必要时发送 OPERATION 命令关断
    │   │                           (详见第 9 章)
    │   │
    │   └── 通信 / 存储器 / 逻辑故障
    │       │
    │       ▼
    │       读取 STATUS_CML 定位具体原因
    │       (PEC 错误 / 无效命令 / 存储器异常等)
    │       执行相应恢复策略
    │
    └── COMM / MEMORY / PROCESSOR 置位
        │
        ▼
        读取 STATUS_CML (0x7E) 获取详细信息
        执行总线恢复或设备重置
```

### 7.6.5 处理完成后的后续动作

完成一轮告警处理后，主机应执行以下操作：

1. **必要时执行 CLEAR_FAULTS**：清除设备中锁存的故障状态。但需注意，`CLEAR_FAULTS` 只清除锁存状态，如果故障的物理条件（如过温）仍然存在，相关位可能立即重新置位（详见第 8 章）。

2. **恢复正常轮询**：返回 NORMAL_POLL 状态，继续周期性采集遥测数据（详见第 14 章主机端驱动开发指南中的状态机设计）。

3. **更新故障计数**：如果系统维护故障计数器，记录本次故障的类型、时间和设备地址，便于后续分析。

## 本章小结

本章讲解了 SMBALERT 中断机制的完整工作原理：

- SMBALERT 是事件驱动的异步通知机制，与轮询驱动互补使用。
- SMBALERT# 采用开漏线或拓扑，支持多设备共享单根信号线。
- ARA 协议（地址 0x0C）使主机能定位报警设备，利用总线地址仲裁实现多设备优先级。
- SMBALERT_MASK 命令可选择性屏蔽特定告警条件。
- 主机端处理应分为 ISR（仅设标志）和后台任务（完整协议处理）两层。
- 告警处理的核心是读取 STATUS 寄存器层级（STATUS_WORD → STATUS_xxx），根据故障类型执行相应策略。
